# 现有方案调研（GNOME + Wayland + 不写系统目录）

调研目标：让 macOS/Linux 双持用户「只记一套快捷键」，且**对终端和应用都生效**。

## 0. 把约束翻译成技术判据

| 需求 | 技术判据 |
|---|---|
| 不污染系统目录 | 全部落点在 `$HOME`；不写 `/etc`、`/usr`、`/var`；不装 udev 规则；不用 root |
| 对终端和应用都生效 | 必须能拿到「当前焦点应用」，才能对终端用 Ctrl+Shift+C（复制）、对普通应用用 Ctrl+C |
| 尽量保证 GNOME 功能正常 | 不能全局交换 Ctrl/⌘；不能悄悄吃掉 GNOME 的 Super 组合键 |
| 目标用户双持 | 需要一套「⌘ = 该应用在 macOS 下的行为」的映射表，而不是把键盘整体改成 Mac |

两条容易被忽略、但决定方案生死的判据：

1. **注入路径**：Wayland 下，普通进程要「合成按键」只有两条路——写 `/dev/uinput`（要权限）或在合成器内部注入（GNOME Shell 扩展）。`wtype` 依赖 `zwp_virtual_keyboard_v1`，GNOME 不实现；`xdotool` 只能影响 XWayland（本机 `~/.local/bin/terminal-console-ctrl-d.sh` 就是这种失败尝试的遗物）。
2. **焦点来源**：GNOME 不实现 `wlr-foreign-toplevel-management`，所以**任何**想按应用区分的方案，要么读 X11 的 `_NET_ACTIVE_WINDOW`（只覆盖 XWayland），要么必须有一个 GNOME Shell 扩展把焦点窗口报出来。

## 1. 方案逐个评估

### 1.1 Kinto（rbreaves/kinto）

- 原理：Linux 侧靠 **xkeysnail**（[README](https://github.com/rbreaves/kinto)），macOS 侧靠 Karabiner。
- 优点：名气最大，键位表齐全；「复制粘贴在所有应用和终端里都能用」的目标与本需求一致。
- 致命问题：xkeysnail 是 **X11 专用**。GNOME Wayland 会话下直接不工作；且安装脚本需要 sudo 并写入系统目录。
- 结论：**不可采用**（除非用户愿意退回 X11 会话）。

### 1.2 keyd（rvaiya/keyd）

- 原理：内核层 evdev/uinput 的 C 守护进程，配置在 `/etc/keyd/`，systemd 系统服务。
- 优点：速度快、layers/overload 等能力最强。
- 问题：
  - 必须 root + 写 `/etc`（违反约束 1）。
  - 「按应用区分」由 `keyd-application-mapper` 提供，而它**只支持 X11**（[issue #694](https://github.com/rvaiya/keyd/issues/694)、[#223](https://github.com/rvaiya/keyd/issues/223)），Wayland 下拿不到焦点应用。
- 结论：**不可采用**。

### 1.3 input-remapper（sezanzeb/input-remapper）

- 原理：Python + 系统守护进程 + GTK 前端，按键/鼠标/游戏手柄映射。
- 问题：通过 `.deb`/发行版仓库安装到系统目录、守护进程以 root 运行；「按应用切换预设」长期是社区讨论项而非一等能力（[discussion #20](https://github.com/sezanzeb/input-remapper/discussions/20)）。
- 结论：**不可采用**。

### 1.4 xremap（xremap/xremap）★ 引擎候选

- 原理：Rust，读 `evdev` → 写 `uinput`，因此 X11/Wayland 通吃；支持 `application.only/not`、`device.only/not`、按键序列、modmap、热插拔 `--watch`。
- 优点：
  - 官方文档就有一节 [running_without_sudo.md](https://github.com/xremap/xremap/blob/master/doc/running_without_sudo.md)：加 `input` 组 + uinput 权限即可**不以 root 运行**。
  - 应用感知在 GNOME 上的实现是「调用一个 GNOME Shell 扩展的 D-Bus 方法」，即**扩展只负责报焦点，按键处理全在用户态进程里**——这正是我们需要的分工。
- 问题（关键）：上游的 GNOME 客户端调用
  `org.gnome.Shell:/com/k0kubun/Xremap → com.k0kubun.Xremap.ActiveWindow()`，
  而上游扩展在 GNOME 45+ 上失效，xremap 启动日志会打印
  `application-client: GNOME (supported: false)`，导致**所有 application 过滤静默失效**（[discussion #818](https://github.com/xremap/xremap/discussions/818)）。在本机 GNOME 51 上我复现了该现象（见 `文档/02-选型与架构.md` 的验证记录）。
  这不是小问题：过滤失效时终端会拿到 `Ctrl+C`（SIGINT），⌘C 从「复制」变成「杀进程」。
- 结论：**采用为引擎，但必须补上焦点来源**（本仓库的 `扩展/` + `mackey 焦点桥`）。

### 1.5 gnome-macos-remap-wayland（petrstepanov）★ 最接近的既有成品

- 原理：xremap + 改 GNOME/Mutter 默认键位 + 用户 systemd 服务，安装.sh 需要管理员密码。
- 优点：与本项目目标几乎一致，且把「改 GNOME 键位」纳入方案（说明这一步是绕不开的）。
- 问题：
  1. 安装.sh 需要 sudo，xremap 装到系统路径；
  2. 依赖上游 xremap 扩展（见 1.4 的失效问题）；
  3. **本机就是它的失败现场**：user manager 里残留着反复启动失败的 `gnome-macos-remap.service`，日志为
     `Unable to locate executable 'xremap': No such file or directory`——系统路径里的二进制在某次镜像更新后消失，用户态服务只剩空转。
     这恰好验证了「安装到系统目录」这条路的脆弱性。
- 结论：**不直接采用，但借鉴其「迁移 GNOME 键位」的思路**，并把「不能依赖系统路径」作为硬约束。

### 1.6 Mac-Keyboard-Style-On-Linux（Anas-Alhariri，2025-12）

- 原理：xremap 实现「三键全交换」：物理 Alt→Ctrl（⌘）、Super→Alt（⌥）、Ctrl→Super（⌃），并按 Apple 官方文档列了完整键位表。
- 优点：**键位表是很好的参照物**（⌘←/→ 行首行尾、⌥←/→ 按词、⌘⌫ 删到行首、⌘⇧[/] 切标签页……）。
- 问题：
  1. 安装脚本需要 sudo；
  2. 三键全交换意味着**Linux 侧的 Ctrl 习惯被摧毁**：物理 Ctrl 变成 Super，Ctrl+C/Ctrl+L 等必须改按 ⌘ 位置那颗键；对「同时在用 Linux」的用户来说这等于把两套习惯换成一套并丢掉另一套。
- 结论：**不采用其映射方式，但吸收其行为清单**（并补齐终端/文件管理器的差异）。

### 1.7 纯 GNOME Shell 扩展（`Clutter.VirtualInputDevice`）

- 原理：扩展里 `seat.create_virtual_device(KEYBOARD_DEVICE)` + `notify_keyval()` 注入按键；用 `global.display.grab_accelerator()` 抢键。
- 优点：零特权、零依赖，`Gio.DBusExportedObject` 就能报焦点。
- 问题（本机已确认 `Clutter.Seat.create_virtual_device` 存在，属于"能做但不该做"）：
  1. **抢不到已被 mutter 抓走的键**（如 Super+Tab、Super+数字），只能改 gsettings 把 GNOME 的绑定删掉再自己实现；
  2. **修饰键污染**：用户按着 Super 时扩展注入 Ctrl+C，应用收到的是 Super+Ctrl+C，GTK 的加速器匹配会失配；要规避就得在注入前把 Super「逻辑释放」，而 mutter 对跨设备释放键的处理不可靠；
  3. 新装扩展必须重新登录才会被 GNOME 扫描（本机实测：即使原子 `mv` 进扩展目录也不会被识别），调试与升级体验差。
- 结论：**不作为按键引擎**；但作为「焦点来源」是最合适的（见 1.4 的缺口）。

### 1.8 XKB / gsettings 层面的静态改键

- 手段：`org.gnome.desktop.input-sources xkb-options`（如 `caps:ctrl_modifier`、`altwin:swap_alt_win`），或用 `$XDG_CONFIG_HOME/xkb` 写自定义 option（libxkbcommon 支持用户目录，不碰系统）。
- 优点：完全用户态、GNOME 原生、零依赖。
- 问题：**静态且全局**——同一个键在任何应用里必须给出同一种结果，因此天然做不到「终端 vs 应用」的区分，也改不了「⌘ 组合 → 另一组修饰键」这种逐组合的翻译。
- 结论：**作为补充**（Caps Lock→Ctrl 之类的开关），不作为主引擎。

### 1.9 注入类小工具

| 工具 | 结论 |
|---|---|
| `ydotool` | 只能注入、不能抓键，也没有按应用区分；本机有它，但仅用于「uinput 是否可写」的环境判据 |
| `wtype` | 依赖 GNOME 未实现的 `zwp_virtual_keyboard_v1`，Wayland/GNOME 下不可用 |
| `dotool` | 同样走 uinput 注入，能力等价于 ydotool |
| `xdotool` | X11 专用；本机残留脚本用它 + 临时改 gsettings 模拟 Ctrl+D，在 Wayland 下无效 |

## 2. 横向对比

| 方案 | Wayland | 无需 root | 不写系统目录 | 按应用区分 | 终端可用 | 结论 |
|---|---|---|---|---|---|---|
| Kinto / xkeysnail | ✗ | ✗ | ✗ | ✓(X11) | ✓ | 不可用 |
| keyd | ✓ | ✗ | ✗ | ✗(Wayland) | ✓ | 不可用 |
| input-remapper | ✓ | ✗ | ✗ | 部分 | ✓ | 不可用 |
| **xremap** | ✓ | ✓ | ✓ | ✓ 需焦点来源 | ✓ | **采用** |
| gnome-macos-remap | ✓ | ✗ | ✗ | ✓ 依赖失效扩展 | ✓ | 借鉴 |
| Mac-Keyboard-Style | ✓ | ✗ | ✗ | ✓ | ✓ | 借鉴清单 |
| 纯 Shell 扩展 | ✓ | ✓ | ✓ | ✓ | ✓ | 只用作焦点来源 |
| XKB 静态改键 | ✓ | ✓ | ✓ | ✗ | ✗ | 补充 |

## 3. 调研结论

1. **能同时满足「Wayland + 无 root + 不写系统目录 + 终端/应用区分」的引擎，实际只有 xremap 一条路**（evdev 读 + uinput 写，用户态运行）。
2. xremap 唯一的断点在「GNOME 焦点来源」上，而它的协议是公开且稳定的（一个 D-Bus 方法），**用我们自己的扩展复刻即可修复，无需改 xremap 源码**。
3. 「按应用区分」这件事在 GNOME 上没有别的廉价替代，因此本方案把焦点来源做成了可替换的两层（扩展 → focusd → xremap），这样上游扩展再次失效时，换一个来源即可，不用动引擎配置。
4. 「改 GNOME 键位」在冲突处无法完全避免；但可以做到**只在真的冲突时改、改前备份、卸载还原、功能平移而不是删除**。
