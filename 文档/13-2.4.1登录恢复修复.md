# 2.4.1 登录与服务恢复修复

## 故障证据

2026-10-14 在 Bluefin 镜像更新后的用户会话中检查发现：HOME 中的 Mackey 二进制、
配置、GNOME 扩展、两项用户服务及自启链接均存在，服务仍为 enabled，输入设备权限正常。
更新未清除安装；当时焦点桥已恢复运行，而引擎处于 inactive。

启动日志显示 GNOME Shell 名称及扩展对象先后不可用，数秒后才可查询。
旧引擎因 `BindsTo` 随焦点桥失败停止，但焦点桥重新启动没有再次拉起引擎。
因此重新安装碰巧恢复了服务，并非每次镜像更新都需要安装。

## 修复方式

- 焦点桥使用 `Type=notify` 与 `NotifyAccess=main`。验证焦点来源、建立 socket、设为
  0600 并准备接受请求之后，才向 systemd 发送 `READY=1`。
- 就绪后通过 `ExecStartPost=systemctl --user --no-block start mackey-engine.service`
  拉起引擎。非阻塞调用避免等待具有 `After` 关系的引擎而产生死锁。
- 焦点桥保留两秒失败重试，关闭启动次数限流；不通过双向 `Wants`/`Upholds` 拉起。
  实测这类依赖与引擎的反向依赖会绕过重试间隔，形成高速失败循环。
- 引擎保留 `BindsTo` 与 `After`。桥接故障时停止引擎，桥接恢复就绪后重新启动。
- 停用时先检查单元是否存在，再在同一 systemd 事务中停用两者；缺失单元仍跳过。

沿用原有两项服务，没有新增监控程序、定时任务或系统配置。
HOME 保留且运行依赖、权限与配置有效时，镜像更新后无需重装。
手动执行 `mackey 停用` 会取消自启并保持关闭，不会被恢复逻辑强行启用。

## 回归验证

独立集成测试 `测试/服务恢复.rs` 使用真实用户 systemd、独立服务名及 HOME 内 socket，
通过 Rust 探针读取真实焦点桥协议，不创建或打开输入设备。

```bash
cargo test --locked --test 服务恢复 -- --ignored --nocapture
```

本机实测通过以下情形，测试耗时约 20 秒：

1. 来源不可用时连续至少六次自动重试，总等待不少于十秒；引擎探针从未执行。
2. 将来源切换为可用并重载单元，不手动启动服务，引擎自动启动且读取有效焦点。
3. 向测试焦点桥发送 SIGKILL，引擎随之停止；来源再次可用后两者自动恢复。
4. 显式停止测试焦点桥，两者保持停止，等待超过重试间隔也没有重启。

测试只链接临时单元而不 enable，结束后清理链接、失败状态和进程。
通知单元测试覆盖文件与抽象通知 socket、无通知环境独立运行及无效通知地址；
隔离安装测试覆盖同一事务停用两项服务和缺失单元处理。

`cargo 检查` 通过 44 项 Rust 测试（20 库、5 命令行、17 安装卸载、2 虚拟键盘参数/ABI），
以及 13 项真实 GJS/D-Bus 断言和 115 映射差分；真实 systemd 回归按上述命令另外执行。

实际重启与下一次镜像更新尚未执行；上述登录来源延迟和进程故障由隔离服务模拟。
实际宿主的升级、配置保全与服务状态另以本机安装结果核验。
