# 选型与架构

## 1. 结论

**分层：xremap（引擎）+ 自研 `xremap-compat` 扩展（焦点来源）+ `focusd`（socket 桥）+ 冲突探测/迁移（策略）+ 行为清单生成器（配置）**

```
        物理键盘
           │  evdev（input 组可读）
           ▼
   ┌──────────────────┐   需要「按应用区分」时
   │  xremap（用户态）│ ───────────────┐
   │  modmap+keymap   │                │  GNOME_SOCKET
   └──────────────────┘                ▼
           │ uinput            ┌───────────────┐
           ▼                   │   focusd      │  （user service）
   GNOME / 应用（拿到 Linux    └───────────────┘
   等价按键：Ctrl+C 等）               │ D-Bus
                                       ▼
                            gnome-shell 内的 xremap-compat 扩展
                            （报当前焦点窗口的 wm_class/title）
```

- 引擎**不做任何按键的「全局交换」**：物理 Ctrl 仍是 Ctrl，物理 Super 仍是 Super。
  只有清单里列出的 ⌘/⌥ 组合被翻译成「该应用在 Linux 下的等价按键」。
- 焦点来源做成可替换的两层，是因为 xremap 上游的 GNOME 扩展已经失效过一次（见 §3）。
- 所有落点都在 `$HOME`：`bin/mackey` 在每次写入前断言路径属于 `$HOME`，并拒绝以 root 运行。

## 2. 关键设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 修饰键策略 | **叠加**（⌘ 组合翻译成 Ctrl 组合）+ 可选**点状替换** | 目标用户「同时在用 Linux」，全局交换会摧毁 Linux 侧 Ctrl 习惯并让终端失去 SIGINT。默认两边都能用；`swallow_ctrl` 可在非终端配置档里吞掉 ⌃C/⌃X/⌃V/⌃Z/⌃A，实现更纯的 macOS 语义 |
| ⌘ 的物理位置 | `modifier_layout=apple` 用原生 Super；`pc-swap` 用 xremap **modmap** 交换 Alt/Win | 实测（见 §3）modmap 在 keymap **之前**生效，所以清单里的触发键在两种布局下都写作 `Super-*`，无需两套配置 |
| 为什么不用 XKB `altwin:swap_alt_win` | 交换放在 modmap 里 | 交换是引擎内部状态：引擎一停键盘立刻恢复；也不会让「合成 Super 键」被 XKB 再翻译一次 |
| 注入什么键 | **原则上只注入 Ctrl/Shift/Alt/F-键**，两处刻意例外：`⌘M → Super+H`（复用 GNOME 自己的 minimize）、`⌘Space → Super 单击`（打开概览搜索） | 注入 Super 会触发 GNOME 自己的绑定、还可能形成回环；例外只用于「复用 GNOME 语义」且已实测通过 |
| 复用 GNOME 自身绑定 | 例：⌘M 最小化 → 合成 `Super+H`（GNOME 的 minimize）；⌘⇧3/4/5 截图 → 合成 `Print`/`⇧Print`/`⌥Print` | 用 GNOME 已有的语义，比硬编码行为更稳，也更符合「保证 GNOME 功能正常」 |
| 类型与静态检查 | Python（`tools/`）全量类型注解 + mypy 严格模式；GJS（`extension.js`、契约测试）`// @ts-check` + 手写 `types/gjs.d.ts`，交给 `tsc --noEmit` | 用类型固化 checklist、生成配置、引擎状态、socket 协议等边界形状，结构改错立刻暴露；不引入打包链，扩展保持单文件、可直接审阅 |
| 冲突处理 | `translate` / `passthrough` / `relocate` 三种，**冲突由 dconf 探测得出** | GNOME 各版本键位不同（本机 GNOME 51 的 `Super+↑/↓` 是空的，更老版本是最大化）；硬编码必然过时 |
| 迁移目标的安全性 | 生成器**硬校验**：迁移目标不得与清单里任何「会吞键」的触发键重合 | 否则 GNOME 功能被自己吃掉（实际开发中就被这条校验抓出 3 处冲突：`Super+S+V`、`Super+S+S`、`Super+S+3/4/5`） |
| 终端安全 | 终端配置档单独一套，且**不参与泛化翻译**；危险键显式吞掉（发射 `F24`） | 泛化会把 ⌘D 变成 Ctrl+D = EOF（关掉 shell）、⌘Z 变成 SIGTSTP（挂起前台进程） |
| 焦点来源 | 自研扩展实现 xremap 期望的 `com.k0kubun.Xremap` 契约 | 复刻契约即可修复上游失效，**不需要给 xremap 打补丁**，也不需要维护 Rust 分支 |
| 额外加一层 socket 桥 | `focusd` 把「任意焦点来源」翻译成 xremap 的 socket 协议 | 换来源不用改引擎配置；同时让整套链路可以在没有真实键盘的情况下自动化验证 |

## 3. 本机验证记录（GNOME Shell 51.0 / Wayland / 无 root）

| # | 验证项 | 方法 | 结果 |
|---|---|---|---|
| 1 | 会话与权限边界 | `id`、`getfacl /dev/uinput`、`ls -l /dev/input` | 用户已在 `/etc/group` 的 `input` 组；`/dev/uinput` 有 uaccess ACL 可写；`/usr`、`/etc` 只读；`sudo` 需要密码 |
| 2 | 上游扩展失效复现 | 用真实 xremap 跑一次 | 日志 `application-client: GNOME (supported: false)` ✔ 复现（问题确认存在） |
| 3 | modmap 与 keymap 的先后 | 虚拟键盘注入物理 `Alt+C`，观察命中哪条规则（探针配置：`tests/probe-modmap.yml`） | 命中 `Super-c` → **modmap 先生效**，清单触发键可统一写 `Super-*` |
| 4 | 焦点桥是否被 xremap 接受 | `focusd` + `GNOME_SOCKET` + 虚拟键盘 | 日志 `application-client: GNOME (supported: true)` ✔ |
| 5 | 按应用分流正例/反例 | `application.only` 分别用 `/.+/` 与 `/this-app-does-not-exist/`，命中动作写文件 | 正例命中应用专属 keymap、反例落兜底 ✔（`tests/e2e-app-match.sh`，可重复运行） |
| 6 | 生成的配置是否合法 | 用生成的 `~/.config/mackey/xremap.json` 真实启动 xremap | 无键名/语法错误，正常进入抓键状态 ✔（键名校验与这一步一起抓出过 `A-Return`、`Page_Up`、`bracketleft` 等非法键名） |
| 7 | GNOME 新装扩展能否热加载 | 复制/原子 `mv` 到扩展目录后 `gnome-extensions list` | **不能**：必须重新登录才会被扫描到（已写入安装说明与 `doctor`） |
| 8 | systemd 用户服务能否补加 input 组 | `systemd-run --user --property=SupplementaryGroups=input`（会话已持有该组时复测） | 失败（`216/GROUP`）：用户管理器无 `CAP_SETGID`，`setgroups()` 必然 EPERM，会话已有该组也一样 → unit 一律不写该指令；用户服务本就继承会话附加组，「加组后重登」即可 |
| 9 | 本机历史遗留 | `journalctl`、`loginctl`、扩展目录 | 发现残留的 `gnome-macos-remap.service` 反复启动失败（petrstepanov 方案，二进制失踪）；`doctor` 会提示清理 |
| 10 | **扩展本身能否被加载、契约是否成立** | 隔离带测试：加载**真实 `extension.js`**，只把 `resource:///org/gnome/shell/extensions/extension.js` 换成桩，桩化 `global.display`，再走**真实 D-Bus 往返**（`tests/verify-extension.sh`，11 项检查） | 全部通过：模块可解析/可实例化；`enable()` 在 `/com/k0kubun/Xremap` 导出 `com.k0kubun.Xremap`；`ActiveWindow` 返回 `{"wm_class","title"}`；`WMClass`/`WMClasses` 正常；**无焦点窗口时返回空串而不抛错**（保证 xremap 退到兜底而不是崩）；`disable()` 撤掉导出 |
| 11 | metadata 是否合法、能否按标准方式安装 | `gnome-extensions pack` | 通过（生成 `.shell-extension.zip`，含 `metadata.json`/`extension.js`） |
| 12 | systemd `ExecStart` 字面量参数的引号规则 | `systemctl --user show -p ExecStart` + 回显脚本，样例含空格、`%`、`$`、`${VAR}`、中文路径 | `%%` 还原 `%`、`$$` 还原 `$`、`\"` 与 `\\` 保留原字符、`${VAR}` 不再被展开；据此修掉「多个或带空格的 `--device` 设备名把 ExecStart 拆坏」（`bin/mackey` 的 `systemd_quote`） |
| 13 | 键位表 vs「全新 GNOME 默认键位」 | 解析 `*.gschema.xml` 的编译 `<default>`，与清单会吞键的触发键求交集，并用 `relocation_plan` 复算覆盖 | 抓出 3 处未计划冲突：`Super+↑`（最大化）、`Super+↓`（还原窗口）、`Super+Space`（输入源切换；旧定义只覆盖 `Super+⇧Space`）→ 已补迁移定义（→ ⌥⌘↑/↓、⌃⌘Space/⌃⇧⌘Space），并加离线回归（`tests/test_generate.py` 第 4g 组） |
| 14 | 截图映射是否贴合 GNOME 行为 | 从 `libshell-51.so` 提取 `js/ui/screenshot.js` 读 UI 实现，并与 dconf 实测绑定对照 | UI 默认就是选区、`s`/`c`/`w` 切 选区/整屏/窗口、内置录制按钮；任何截图都同时进剪贴板与文件。据此让 `⌘⇧3/4/5` 的输出全部从实测绑定推导（改绑后跟随），并分别对应 GNOME 的 选区（交互式 UI）/屏幕（全屏直接落盘）/窗口（截当前窗口）；窗口键由原生条目升级为映射条目，且保留离线回归（`tests/test_generate.py` 第 4i 组） |

未能完成的验证及其原因（如实记录）：
- 想让 gnome-shell **自己**加载扩展并检查状态：`gnome-shell --headless` 在本机段错误；
  `gnome-shell --wayland`（嵌套）报 `Failed to take control of the session: EBUSY`
  ——因为用户会话已经占着 logind 会话。嵌套/headless 两条路都不通，所以改用上面的隔离带测试，
  并把「扩展变 ACTIVE」留给用户重新登录后用 `mackey doctor` 一句话确认。
- 需要真实键盘才能判定的观感问题（⌘Space 合成 Super 后概览是否「闪一下就关」、⌘M 触发
  GNOME minimize 后抬手 Super 会不会唤起概览）只能在重新登录后手动确认，已在清单备注里写明退路。

测试手段说明：为了**不碰真实键盘**，验证用 `tests/fake_keyboard.py` 造一个独立虚拟键盘
（`--device mackey-test-kbd` 只抓它），命中动作写成 `launch: touch <文件>`，于是「哪条规则生效」
直接看文件名即可。注意：未被映射、需要透传的键由 xremap 照常转发到当前焦点窗口
（替换模式的 Ctrl+C 例外正是这样验证的），跑端到端时不要让敏感窗口抢焦点。

## 4. 与 GNOME 的冲突处理（本机实际探测结果）

本机 GNOME 51 共占用 100 个加速键（去重后），其中 18 条与 macOS 高频快捷键冲突。默认策略是
**把 GNOME 功能平移到新组合**（而不是删除），且只在检测到冲突时才写 dconf：

| GNOME 功能 | 原按键 | 迁移到 | 为谁让路 |
|---|---|---|---|
| 应用网格 | ⌘A | ⌥⌘A | ⌘A 全选 |
| 通知托盘 | ⌘V / ⌘M | ⌥⌘V / ⌥⌘M | ⌘V 粘贴、⌘M 最小化 |
| 快速设置 | ⌘S | ⌥⌘S | ⌘S 保存 |
| 显示桌面 | ⌘D | ⇧⌘D | ⌘D 收藏/复制 |
| 聚焦通知 | ⌘N | ⌥⌘N | ⌘N 新建 |
| 切换显示器 | ⌘P | ⌥⌘P | ⌘P 打印（XF86Display 硬件键依旧可用） |
| 左右半屏平铺 | ⌘← / ⌘→ | ⌃⌘← / ⌃⌘→ | ⌘←/→ 行首行尾 |
| 窗口移到其他显示器 | ⇧⌘←↑↓→ | ⌃⇧⌘←↑↓→ | ⇧⌘←/→ 选中到行首行尾 |
| 程序坞第 N 个应用 | ⌘1…⌘9 | ⌃⇧⌘1…⌃⇧⌘9 | ⌘1…9 切换标签页 |
| 锁屏 | ⌘L | ⌃⌘Q（= macOS 的锁屏键） | ⌘L 聚焦地址栏 |
| 输入源切换 | ⇧⌘Space | ⌃⌘Space | ⌘Space 聚焦搜索 |

> 完整 23 条（含逐键展开）见 `docs/03-行为清单.md`，由生成器自动产出。
> 选择 `⇧⌘X`/`⌥⌘X` 作为迁移目标的原因：它们在 GNOME 默认键位里是空的，且**不会与清单里的触发键重合**（这条由生成器硬校验保证）。

### 默认放行（不改 GNOME）的冲突

| 组合 | 为什么放行 |
|---|---|
| ⌘Q | GNOME 的「关闭窗口」与 macOS 的「退出应用」语义天然接近 |
| ⌘H | GNOME 的「最小化」是 GNOME 没有「隐藏应用」概念下最接近的行为 |
| ⌘Tab / ⇧⌘Tab / ⌘\` | GNOME 原生语义与 macOS 完全一致 |
| ⌃↑ / ⌃↓ | 在 Linux 上是「按词/段落移动」，接管代价大于收益，默认关闭（清单里标为可选） |
| ⌃← / ⌃→ | 同上（切换桌面空间在 GNOME 侧仍是 ⌘PgUp/PgDn、⌃⌥←/→） |

## 5. 已知限制与风险

1. **唯一特权前提**：读 `/dev/input` 需要 `input` 组。这是 evdev 方案的固有代价，且意味着
   「任何以你身份运行的进程都能读键盘」。本工具不做这件事，只在 `doctor` 里检查和提示。
   （本机该组已在 `/etc/group` 中配置，但**当前会话是加组之前建立的**，需要重新登录才生效。）
2. **两次重新登录**：① 加 `input` 组后；② 新装 GNOME 扩展后（Wayland 下 GNOME 不热扫描扩展目录）。
   这两点都已写入 `install` 的输出与 `doctor` 的提示，不会静默失败。
3. **焦点失效 = 终端危险**：焦点来源不可用时，xremap 会让所有键走兜底 keymap，
   终端里的 ⌘C 会退化成 Ctrl+C（SIGINT）。`doctor` 会以红色告警这一项，这是刻意的。
4. **文件管理器/终端的第三个配置档依赖 wm_class**：Flatpak 应用、VS Code 内置终端等
   无法按窗口内区域区分（VS Code 内置终端属于 `code` 窗口，按普通应用处理；
   它自身的按键设置里可以再单独调整）。
5. **合成按键的兼容性**：个别应用对合成按键不敏感（Wayland 下的既有通病），
   可用 `keypress_delay_ms`（配置项，已留）缓解。
6. **上游依赖**：引擎是第三方二进制。默认由 `mackey fetch-engine` 按指令集架构 + 桌面环境
   下载上游最新发布版本（`xremap-linux-<arch>-<feature>.zip`，装到
   `${XDG_DATA_HOME:-~/.local/share}/mackey/bin/xremap`，不写系统路径、不调 sudo），
   也可以用 `cargo install xremap --features gnome` 或手放到仓库 `.vendor/xremap`。
   GNOME 大版本升级后焦点扩展的 API 可能变化，届时只需改 `extension/extension.js` 一个文件。
7. **泛化翻译的边界**：清单未列出的 ⌘+字母/数字会被泛化成 Ctrl+同键，与 GNOME 已占用键位自动互斥；
   个别键可用 `sweep.exclude_triggers` 点名排除（当前排除 `⌘U`：Ctrl+U 在 GtkEntry/GtkText 里是「清空输入框」，
   误触发代价大）；终端不参与泛化。
8. **点状替换的例外**：`swallow_ctrl` 通过独立 keymap + `application.not` 实现，
   例外名单 = 终端配置档 + `except_apps`（默认 VS Code / JetBrains / GNOME Builder / Emacs 等
   带内嵌终端的应用）。因此真实终端与这些 IDE 的内嵌终端里 `⌃C` 仍是 SIGINT、`⌃A/Z/W/L` 仍是 readline；
   其余应用里这 5 个组合被吞掉、只保留 ⌘ 版本。换了新的编辑器？把它的 wm_class 正则加进
   `except_apps` 并 `mackey generate` 即可。
   终端里另有一层 `swallow_terminal`：物理 `⌃⇧C`/`⌃⇧V` 被吞掉，复制/粘贴只保留 `⌘C`/`⌘V`
   （⌘ 路径输出的是引擎合成的 `⌃⇧C`/`⌃⇧V`，xremap 不读自己合成的按键，不经过这层拦截）；
   不带 Shift 的 `⌃V` 特意不吞，readline 的 quoted-insert 等仍可用。

## 6. 后续可扩展方向

- 图形化的偏好设置（GNOME 扩展 prefs 或独立 GTK 窗口），把冲突策略暴露成开关。
- 按窗口标题（而不只是 wm_class）细分，例如区分「VS Code 主窗口 / 内置终端」。
- 可选的 Caps Lock→Ctrl / Caps Lock→Esc（纯 `xkb-options`，已在方案里预留但默认不动用户的输入源设置）。
- 追加 ⌃↑/⌃↓ 的 opt-in 映射（清单里已列，默认关闭）。
